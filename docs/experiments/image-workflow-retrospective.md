# 图片处理流程复盘与优化

日期：2026-09-09。依据本次实际操作、当前代码和[独立上传实测记录](independent-image-upload.md)，不把模拟测试等同于线上验证。

## 经过与问题

1. README 增加 banner 后，旧插件先因不认识新主题而无法读取项目记录；使用更新的客户端后，又遇到“所有嵌入资源一律阻止”的发布限制。
2. 初次实现直接选择了本地图片转 Base64、随正文加密。该方案能够工作，但没有先核对上游独立上传协议，就把实现范围当作服务能力边界。这是本次决策的主要问题。
3. 用户要求核对独立上传后，真实服务测试证明 `/v1/file/upload` 可用，附件 URL 可匿名读取，按哈希可复用。随后在明确公开授权下，将已有 GitHub 页面原地转换成公开正文和独立图片引用。
4. 多次更新内容相同的 README，仍然重复提交正文；另一个已不存在页面也多次进入候选。返回分享链接还依赖临时脚本，缺少正式的受控接口。

## 优化原则

- 区分服务协议能力、仓库实现能力和实际安装包能力。不能从旧客户端报错推断上游不支持；涉及新能力时先运行实际安装包的离线能力查询。
- 正文可见性和图片存储方式是两个概念。当前支持加密正文＋内嵌图片，以及已有主题页面的公开正文＋独立图片。不能因为用户要求独立上传，就擅自公开正文；未实现的组合必须明确说明。
- 更新先锁定源文件、主题和活跃记录，复用此前仍适用的用户选择。多个活跃目标确实无法区分时才询问，不按更新时间猜目标。
- 预览是决定是否可发布的检查点。公开服务模板限制、图片数量、大小、处理方式及可见性应在这里体现；不能先显示可发布，执行更新时才发现已知限制。
- 内容未变也要核验远端基线和图片，但无需再次提交正文。只有匹配核验成功，才能报告“内容一致，未重复写入”；不能仅比较本地源文件哈希。
- 未决操作和已失效记录必须在列表中可见。附件上传不确定时不能自动重试，也不能用“pending 为零”暗示没有未决操作。
- 获取链接是读取操作，应使用专用接口，不直接解析私有密钥文件，不为得到链接再发布一次。

## 落地范围

| 问题 | 插件改进 | 验证边界 |
| --- | --- | --- |
| 旧缓存包与仓库功能不一致 | 离线 `capabilities` 报告实际运行包的协议、预览 schema、主题及支持模式 | 不需要配置、凭据或网络；不等于远端实例能力检测 |
| 图片处理和公开范围不清楚 | 预览返回图片模式、文件数、出现次数、字节数和可见性 | 预览不上传，大小按重复引用累计 |
| 公开正文已知限制发现太晚 | 服务模板替换序列在预览中阻止，写入端继续防御检查 | 不放宽净化器或用字符串逃逸绕过服务行为 |
| 重复提交相同内容 | 更新匹配最终正文、标题、主题及模式时跳过正文写入 | 基线冲突、模式或图片变化不能被误判为未变 |
| 已删除目标仍被选中 | 列表保留审计历史，同时显式暴露活跃状态、加密状态、删除时间 | 活跃只描述本地记录，不代表刚刚在线探测成功 |
| 未知上传无法定位 | 列表返回未决操作及附件状态计数 | 不泄露密钥，也不自动恢复未知写入 |
| 临时脚本读取分享密钥 | `link` 从准确项目记录解析分享 URL | 公开 URL 无片段；加密链接仅在用户索取时返回；不声称已验证远端可用 |

## 保持的边界

本轮不扩大允许的图片格式、源目录或服务来源，不改变新分享默认加密模式，不新建或更新远端文章，不删除已上传附件，不发布 Git 版本。用户已有的未提交文件和插件资源保持原样。

文件头和尺寸校验不等于图片完整解码或像素内容审查。独立上传图片的公开 URL 不受正文密钥保护，删除笔记也不保证删除附件。浏览器显示验收、字节回读和自动化回归测试应分别报告。
